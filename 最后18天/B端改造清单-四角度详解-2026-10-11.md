### 1.2 核心问题：parent_classshow 是死 UI

**位置**：`pages/index/parent_classshow/parent_classshow.wxml:44`

```xml
<view class="card" wx:if="{{latestRequest.status === 'scheduled' && latestRequest.coachSchedule}}">
  <!-- 已安排课程：课程名/时间/地点/教练/说明 -->
</view>
<view class="card" wx:else>
  <!-- 永远走到这里："等待教练安排" -->
</view>
```

**为什么永远是"等待教练安排"**：

1. **状态映射断裂**：B 端 `login_index.js:300-308` 只有 4 档（pending / scheduled / finished / cancelled），A 端 `courseState.js:33-41` 有 7 档（editing / awaiting / in_progress / completed / cancelled / closed / pending）。A 端回抄过来的是 `fulfill_state`，经过 `buildCourseStatusFromSnapshot`（`twowaybinding_1_DLforP/index.js:168-185`）压缩成 4 档：

   - `closed` / `completed` → `finished`
   - `cancelled` → `cancelled`
   - `in_progress` 或 `progress_done>0` → `scheduled`
   - 其余 → `pending`

2. **editing / awaiting 两种状态在 B 端全部回落到 pending**，所以家长看到的一直是"待安排"，即使教练已经在 A 端确认了课程。

3. **coachSchedule 永远为 null**：`twowaybinding_1_DLforP/index.js:348` 写的是 `coachSchedule: resultSnapshot.latest_lesson || null`。但 A 端 `buildCoachResultSyncPayload`（`_common.js:322`）里的 `latest_lesson` 是课节摘要（startedAt/completedAt/rating），**不是课表**（courseName/courseDate/location/coachName）。字段结构完全对不上——A 侧从来没写过 `coachSchedule` 所需的 5 个字段，`parent_classshow.wxml:46-50` 判了也永远是空。

### 3.4 dev_ForP 文档结构隐患

**内嵌数组膨胀**：`P_CourseFormCollection` 和 `P_CourseWithCoach` 是内嵌数组，每次提交约课 append 新对象。如果一个家长反复提交（换教练/重新约），这两个数组会越来越大。

- TCB 单文档上限 16MB
- 当前每次 `submitBooking` 写入时用 `_.set()` 整数组覆盖（`login_index.js:1634-1641`），意味着每次提交都要读写整条家长文档
- `upgradeLegacyParentDoc`（行641-750）在每次 `login` 时都会检查并可能执行迁移，成本高

**建议**：

- P0：`buildLatestRequest` 不需要每次遍历全数组，已经有 `latestFormId` / `latestCourseId` 快速定位
- P1：长期考虑把 form/course 拆成独立集合，主文档只保留 ID 引用

### 4.3 核心问题

#### ① B→A 全用 HTTPS GET，payload 放 queryString

**位置**：`login_index.js:468-510`

```javascript
function requestAHttpApiAt(baseUrl, payload = {}) {
  const queryString = buildQueryString(payload);
  const requestUrl = queryString ? `${baseUrl}?${queryString}` : baseUrl;
  return new Promise((resolve, reject) => {
    https.get(requestUrl, ...);
  });
}
```

**问题**：

- URL 长度限制：`submitBooking` 的 payload 含 `childProfiles`（JSON.stringify 后放进 query），多孩子时可能超浏览器/服务端 URL 长度限制（通常 2KB-8KB）
- 无显式超时：`https.get` 没设 timeout，DNS/TCP 层挂住时整个云函数卡死（TCB 默认 20s 强杀，但 20s 内其他请求排队）
- 无重试：B→A 只在「路由级失败」时回退旧地址（`login_index.js:532-557`），网络抖动导致的 JSON 解析失败不重试

**对比 A→B**：A 端 `_shared/http.js` 有 20s 显式超时 + 统一错误处理，比 B 端健壮。

#### ② callHTTPFunction vs callFunction 混用

| 函数                  | 前端调法                        | 原因                              |
| ------------------- | --------------------------- | ------------------------------- |
| DLforP__do          | `wx.cloud.callFunction`     | 普通云函数                           |
| DLforP_entry_qrcode | `wx.cloud.callHTTPFunction` | HTTP 云函数（scf_bootstrap 监听 9000） |

**问题**：

- `callHTTPFunction` 要求基础库 ≥ 3.15.1，`parent-api.js:64` 有兜底提示但用户不一定升级
- HTTP 云函数冷启动更慢（需要启 Node 进程），`parent-api.js:78-81` 用 500ms 重试缓解，但第一次调用仍然慢
- 两种调法的响应结构不同（`res.result` vs `res.data`），`parent-api.js:100-109` 做了兜底解析

#### ③ A→B 回抄地址修正后仍有残留

**A 端 `_shared/http.js:42-47`**：

```javascript
bTwowaybinding: `${B_TENCLOUD_BASE}/twowaybinding_1_DLforP`,
```

10-09 修正了域名（从 A 环境改到 B 环境），但**路径 `/twowaybinding_1_DLforP` 是固定的**。

**问题**：拆双函数后（10-10），B 端 `twowaybinding_1_DLforP` 是否也要拆成 `D_twowaybinding_1_DLforP` / `T_twowaybinding_1_DLforP`？

- **当前状态**：B 端 `twowaybinding_1_DLforP` 只有 1 份，没拆
- **A 端发请求**：只走一条路径 `/twowaybinding_1_DLforP`，不管 envVersion
- **B 端函数内部**：自己有 `applyEnvVersion`（行72-97）按 envVersion 切 dev_/real_ 集合

**结论**：B 端 twowaybinding_1_DLforP **不需要拆双函数**——它内部已经按 envVersion 分流集合了。但如果未来 dev 和 real 要分环境部署（不同云环境），则需要拆。当前无问题。

#### ④ B→A 回退逻辑的风险

`login_index.js:532-557`：

```javascript
async function requestAHttpApi(payload = {}) {
  const primaryUrl = resolveADLforCUrl(CURRENT_ENV_VERSION);
  let result = await requestAHttpApiAt(primaryUrl, payload);
  if (!isARouteMiss(result)) return result;
  // 兜底回退旧地址
  return requestAHttpApiAt(A_DLFORC_URL_LEGACY, payload);
}
```

**风险**：如果 primary 地址返回的是业务失败（`success: false` 但 HTTP 200），不会回退——这是对的。但如果 primary 返回 `success: true`（A 侧建单成功），同时 legacy 地址也被调到了（之前网络抖动走了 fallback），**同一笔约课会被 A 侧创建两次**。

**缓解**：`isARouteMiss` 的判定逻辑（行515-530）排除了业务成功的响应，所以正常情况下不会重复建单。但**并发场景**下（B 端提交后网络超时，用户重试），第一次请求可能还在 A 侧处理中，第二次请求到达时 A 侧可能已经完成第一次——两笔相同约课被创建。

**建议**：A 端 `syncParentBookingToA` 需要做幂等校验（按 `from_b_form_id` 去重），当前代码未确认是否做了。

### 4.5 envVersion 透传链路

```
B 端前端（parent-api.js:36）
  → wx.cloud.callFunction({ data: { envVersion: getMiniEnvVersion() } })
    → DLforP__do（login_index.js:1868 applyEnvVersion）
      → requestAHttpApi（login_index.js:452 envVersion: CURRENT_ENV_VERSION）
        → A 端 twowaybinding_1_DLforC（按 envVersion 分流 NDLdev_/NDLreal_）

A 端回抄（_sync.js → requestBHttpApi）
  → A 端不透传 envVersion 给 B（因为 B 侧 twowaybinding 内部自己按入参切）
  → 但 B 侧 twowaybinding 的 HTTP 入口没有 envVersion 参数
```

**问题**：A→B 回抄时，`twowaybinding_1_DLforP` 的 `exports.main`（行560+）里 `applyEnvVersion(event.envVersion)` —— 但 `event.envVersion` 来自 HTTP query string，A 端发请求时**传没传 envVersion**？

**验证**：看 `buildCoachResultSyncPayload`（`_common.js:296-330`），payload 里没有 `envVersion` 字段。`requestBHttpApi`（`_sync.js:38-42`）直接 `getJson(ENDPOINTS.bTwowaybinding, payload)`，也不加。

**结论**：A→B 回抄时 B 端的 `applyEnvVersion` 收到空字符串，默认走 `release` → `real_ForP`。**如果开发环境的回抄，A 端 dev 侧发 HTTP 请求给 B 侧，B 侧写的是 real_ForP——开发态数据写到正式库**。

这是一个 **P0 bug**：A→B 回抄必须透传 envVersion。
